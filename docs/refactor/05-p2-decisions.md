## 2. 揭晓　`POST /:id/reveal`

照 03。请求体 `{ cue }`：在找、列表、详情里是 `masked`；在试一条里放弃是放弃时所在的那一级。

- 条目没被遮着（不在想用层，或者已毕业）：什么都不写，返回普通详情。
- 否则在**同一个事务**里写 `reveal` 行（`text` 是空串）再读原文，返回 `toDetail(entry, true)`（01:177、03:530 的原话）。两头都守住：行写不进去，原文不出去；行写进去了而原文没读出来，事务回滚，流水账上不留一行"看过"。后一半是 2026-11-25 补的，之前是先写后读、不在事务里，读失败会留下一行并白白推迟一天。两头各有一个测试。
- 揭晓不改变遮挡状态。下一次读列表或详情仍然是遮着的，再看一次就再写一行。

## 3. 试一条

### `GET /try?exclude=1,2`

照 03。`testableAt(库, now)` 去掉 `exclude` 里的 id，取前 3 条。`exclude` 只有 id，不是私人文本，可以放在查询串里。

每条：有 `next_scene` 就 `{ prompt: next_scene, cue: "none" }`，没有就 `{ prompt: intent, cue: "need" }`。`hasScene` 见下。

### `GET /:id/scene`

照 03，补全了匹配方式。取最早那条 `met` 行：焦点非空、并且原文里找得到焦点（不分大小写）时，把每一处焦点换成 `____` 返回，上文里出现的焦点同样换掉。否则 404 `NO_SCENE`。不写任何行，级别由作答请求上报。

### `POST /:id/attempts`

请求体 `{ text, cue, prompt }`，成功是 201 加 `AttemptResponse`。

- **补全：** 条目不在想用层、或者已经毕业，回 409 `NOT_ACTIVE`。03 说毕业的条目「产生不了会让它降档的作答」是靠界面不出题，这里在服务端也挡一道。排队中的条目可以作答：那是用户在「找」里自己撞上的，是最硬的一种证据。
- **补全：** `cue` 是 `none` 时，`prompt` 必须等于条目现在存着的 `next_scene`，否则 400。03 说的是「条目没有 `next_scene` 时不接受 `none`」，这里多比一下内容，顺带挡住「没用上之后带着旧题面又报了一次 `none`」。
- `prompt` 等于存着的 `next_scene` 时（不论 `cue`），在写 `attempt` 行的同一个事务里把 `next_scene` 清掉。在「找」里先试写时题面是用户的需求，不会碰到存着的情境。
- 然后调判定，不在事务里。成功：`outcome` 记 `used ? "pass" : "fail"`，`feedback` 补 `status: "done"`、`used`、`conveyed`、`rewrites`（至多 2 条）、`judgedAt`；模型给的 `nextScene` 过一遍和补注相同的检查（不含目标表达）再写回，条目上已经有情境就不覆盖。回填时带条件 `outcome is null`，重复的判定只有第一个生效。
- 失败：`feedback.status` 记 `failed`，`outcome` 留空，响应里 `status: "failed"`，HTTP 仍是 201。句子已经在库里。

`AttemptResponse` 三条路由共用一个组装函数：

| 字段 | 取值 |
|---|---|
| `verdict` | 模型的读法：`used` 为真是 `used`，否则 `conveyed` 为真是 `conveyed`，否则 `missed` |
| `outcome`、`overturned` | 现在算数的结论，和它是不是用户改过的 |
| `answer` | 原文、焦点、补注。**不给**的情形有两种：还没有判定（`outcome` 为空，判定没回来）；`cue` 是 `none`、`outcome` 是 `fail`、而且这一行从没被推翻过。折叠函数对这两种行的读法相同：答案没上过屏幕 |
| `intent` | 只在后一种情形下给（判了、没用上、不给答案） |
| `rewrites` | 不给答案时是空数组（改写里多半就有答案），其余照存的给 |

### `POST /attempts/:encounterId/judge`

照 03。不存在或不是 `attempt` 行：404。已经有 `outcome`：直接返回现状，不调模型。否则重判，回填在同一行上。

已知的口子，没有堵：对一条已经判过的行再调一次，答案会再给一次，而流水账上不多一行。页面不会这样调；03:540 把"恶意的客户端"放在范围之外，这里照办。

### `POST /attempts/:encounterId/overturn`

**补全，03 只写了一句。** 请求体 `{ outcome }`。

- 还没判定的行：409 `NOT_JUDGED`。
- 和现在的结论相同：不动，返回现状。
- 否则改 `outcome`；`feedback.modelOutcome` 只在第一次推翻时写（模型原来的结论）；`feedback.overturned` 记「现在的结论是不是和模型的不同」，所以推翻两次回到原处是 `false`，推翻率不把它算进去；`feedback.judgedAt` 改成现在。
- 响应里一定带答案。原因在折叠函数里：被推翻过的行，不论方向，答案都上过屏幕（模型判用上了，答案当时就亮了；模型判没用上而用户改成用上，答案在这一刻亮）。01 的参考实现只看 `outcome`，推翻一次就会把「看过答案」抹掉；`fb17259` 起折叠函数多读一个 `modelOutcome`，用例 s。

### 已知的边角：迟到的判定和隔天的推翻

折叠函数照 03 的参考实现，按 `created_at` 顺序过每一行，「看过答案的时刻」只留一个最大值；一条作答行贡献的是 `judgedAt`（判定回来的时刻，推翻时改成推翻的时刻）。所以当一行的 `judgedAt` 晚于**后面另一行**的 `created_at` 时，后面那一行会被拿去和一个它发生时还不存在的「看过」比较，本来算数的一次升档会消失。01:214 的规则原话是「作答之前 24 小时内没看过答案」，按这句话那次升档应当保留。

要走到这一步，得同时满足：同一条目有两次作答；前一次的判定是隔了很久才回来的（当时模型失败，之后点了「再判一次」），或者前一次是隔了很久才推翻的；而「再判一次」和「推翻」只在作答当时那张卡片上有，卡片得一直开着，中间那次作答还得来自另一个标签页或「找」。单人使用几乎碰不到，所以没有改。

真要改不是只换成「按时刻取看过」这么简单：推翻会把 `judgedAt` 覆盖掉，第一次亮答案的时刻就丢了，得在 `feedback` 里把两个时刻都留着，折叠函数再各读各的。估计 15 行上下，加两个用例。

## 4. 找　`POST /find`（历史接口，现已并入对谈）

请求体 `{ need, attempt?, history, turn, thread }`。

1. **单个英文词而且有词卡**（`^[A-Za-z][A-Za-z'’-]*$`，词卡按不分大小写匹配）：不调模型，返回 `card`，`mine` 是 `norm` 等于这个词的条目。**补全：** 这条路上的命中一律不遮。用户自己把这个词打出来了，这次查询就算附了英文。
2. 否则拼索引调一次模型。每行 `id | 焦点（没有就取原文前 80 个字符）| 提示句 | AI 写的意图`，后两格各截到 100 字符。顺序：想用层，然后见过层从新到旧，然后已收起的。字符预算是一个常量（先定 60,000），放不下的不放，`searched` 和 `total` 如实报。
3. 模型返回的 id 不在这次给出去的候选里的丢掉，重复的去掉，**补全：** 至多留 5 个。原文一律来自数据库。
4. **补全：** 模型的 `fresh` 里如果有一条包含了库里某个条目的目标（焦点，没有焦点就是整句原文；不分大小写，按词边界匹配），那它不是新说法：这条从 `fresh` 里拿掉，对应的条目补进 `mine`。不这样做的话，模型一句「新说法」就能把遮着的条目的英文送上屏幕，而时间线上没有任何一行记着。`fix` 不拿掉（那是用户自己的句子改对了），它用到的条目补进 `mine`，各记一行。
   - 词边界按拉丁字母算（`66ba903`）：中文理由引用英文时两边不留空格，「和dawned on差不多」里的汉字原先被当成字母，目标就认不出来。
   - **认不出来的两种，记下来没有做：** 遮着的焦点换了词形（库里是 dawned on，模型写 dawns on）；没有焦点的遮着条目被部分引用或改写（它的目标是整句，而帮我挑和「收」下来的建议都不带焦点）。做词干匹配会误伤（现有测试特意钉着 swamped 不等于条目 swamp；误判的代价是拿掉一条好建议），而真模型多久犯一次还没量过。prompt 里要求「不要在理由里引用索引里的其他条目」是第一道，匹配是第二道。页面还有一层：这一轮有遮着的命中时，`fresh` 先不显示，等命中都试过或看过。
5. 遮挡：命中是遮着的条目、并且这次没有附英文，就 `toSummary(e)`（遮着），`why` 给 `null`，`looked_up` 行的 `cue` 记 `masked`。附了英文则 `toSummary(e, true)`，`cue` 留空，折叠时算作看到了答案。
   - **补全（`722baf7`）：** 任何一条理由（命中的、`fix` 的、`fresh` 的）只要说出了一个「这次回答没有亮出来的遮着条目」的目标，就整条置空。没亮出来的，指所有遮着的条目里除去「附了英文的提问的命中」。
6. 落库：每个命中一行 `looked_up`，没有命中则一行、`expression_id` 为空。`text` 是需求，`my_attempt` 是尝试，`feedback` 是 `{ turn, thread }`，这一次的各行共用一个 `created_at`。
7. **补全：** 模型调用失败回 502 `FIND_FAILED`，什么都不写。需求还在页面的输入框里，重试不会在流水账里留下两次提问。

`fresh` 至多 2 条。`fix` 只在附了英文时要。历史至多 `FIND_HISTORY_TURNS` 轮，和索引、需求一起放在数据区。

页面上的三处，和 01、03 的字面有出入或者是它们没写到的：

- **词卡链接是私人文本进查询串的唯一例外。** 问的是一个有词卡的单词时，回答里的「词卡」链接是 `/cards?prefill=<这个词>`，词卡页随后请求 `GET /api/cards?search=…`。这个词会进地址栏、访问日志和 Service Worker 的词卡缓存。没有改成按 id 打开：计划要的就是一条词卡链接，这个词本身有一张公开的词卡，留下的痕迹和任何人搜一次它一样；按 id 打开要在旧的词卡页里加 15 到 20 行。README 的"权限与安全"里写明了。
- **在「找」里点「收」撞上已有条目，回答是"已收过"，不问"又一次遇到还是另存"。** 只有 `fix` 会撞上（`fresh` 里撞上的已经被第 4 条挪进命中了），而那一条就在这一轮的命中里，自己有一行。
- **在「找」里把命中「放进想用」，条目已经有提示句时不覆盖。** 01:186、03:522 的字面是"需求变成提示句"。这里只在条目没有提示句时才把需求写进去（`intentBy: "find"`）：用户自己写过的那一句被一次提问悄悄换掉，是丢数据。要按字面来是 `FindThread.tsx` 里一行的事。

## 9. 错误码

| 状态 | code | 何时 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 请求体不合 schema；`cue: "none"` 而题面不是存着的情境 |
| 400 | `INTENT_REQUIRED` | 进想用层没有提示句 |
| 404 | `NOT_FOUND` | 条目或作答行不存在 |
| 404 | `NO_SCENE` | 这一条没有原场景这一级 |
| 409 | `DUPLICATE` | 同 `norm` 已存在 |
| 409 | `NOT_ACTIVE` | 对不在想用层或已毕业的条目作答 |
| 409 | `NOT_JUDGED` | 推翻一条还没判定的作答 |
| 502 | `ANNOTATE_FAILED` / `FIND_FAILED` / `PICK_FAILED` | 模型调用失败 |

判定失败不是 HTTP 错误：作答已经落库，响应里 `status: "failed"`。

## 10. 本机试用的开关（偏离 03 第 1.5 节，用户 2026-11-25 要求）

03 第 1.5 节的规则是「没设 `AUTH_TOKEN` 时拒绝服务，不放行」。用户在试用阶段要求表达页面暂时不设密码。没有改默认行为，加了一个明说的例外（`d89841e`，`bf07e47` 收紧）：

- `EXPRESSIONS_OPEN_LOCALLY=1` 时，`requirePrivate` 放行同时满足这些条件的请求：没设 `AUTH_TOKEN`；`NODE_ENV` 不是 `production`；请求是这台机器发给自己的。
- 「这台机器发给自己的」看三样（后两样是 `bf07e47` 加的）：
  - 套接字的对端是本机（`127.0.0.1`、`::1`、`::ffff:127.0.0.1`）。
  - `Host` 的主机名是 `localhost`、`127.0.0.1` 或 `[::1]`。只看套接字挡不住 DNS 重绑定：任何网站的页面可以在加载之后把自己的域名改指到 127.0.0.1，它的请求从本机浏览器发出，对浏览器是同源的，也过得了 `app.ts` 的 Origin 检查（那个检查比的是 Origin 和 Host 是否同名）。重绑定的请求带的是那个网站的名字。
  - `X-Forwarded-For` 里列出的每个地址都是本机。`vite.config.ts` 给开发代理开了 `xfwd`：用 `vite --host` 把页面开给局域网时，别的设备的请求经代理转一手，套接字是本机的，这个头里是它自己的地址。头只会让守卫更严，伪造它得不到任何东西。
- 设了 `AUTH_TOKEN` 开关就不起作用。生产模式没有 `AUTH_TOKEN` 时 `index.ts` 根本不启动，所以线上实例不会因为漏配什么而落进这个分支。
- 放行的响应照样 `no-store`；其余的私人数据规则不变。启动时打一行警告，503 的那段页面提示里写了这个开关。
- **限度：** 一个不报来源地址、又把 `Host` 改写成本机名字的反向代理或隧道（比如不带任何 `proxy_set_header` 的 nginx），在服务端看来和本机没有区别。这个开关不是给那样的服务用的，README 里写了。
- 没设 `AUTH_TOKEN` 的开发模式下，其余的管理接口（生成、删除、设置）对连得到端口的机器、对重绑定的网页本来就是开着的，这不是这次引入的，`bf07e47` 也没有动它；服务监听的是所有网卡。在不可信的网络上试用，还是设 `AUTH_TOKEN`。
